# LawBench 企业级 AI 技术栈实战与面试准备总纲

更新时间：2026-08-22

## 一、最终目标

在现有 LawBench 基础上，逐项补齐企业级 AI 能力，并完成：

- 可运行的代码实现；
- 可复现的测试证据；
- 清晰的数据流和架构解释；
- 常见面试问题与回答；
- 一套完整端到端演示流程。

目标不是堆叠框架，而是做到：

```text
能运行、可验证、可追踪、可恢复、可评测、可解释
```

## 三、必须实操的企业级模块

1. 数据采集、清洗、脱敏、去重、版本和增量更新；
2. 文档切分、元数据、父子文档和知识库构建；
3. 混合检索、RRF、Reranker、权限过滤；
4. 模型网关、模型路由、降级、重试、流式输出；
5. Agent 参数校验、循环限制、Tool 异常和状态持久化；
6. 引用绑定、答案溯源、事实校验和拒答机制；
7. 评测集、Recall、Precision、引用准确率和回归测试；
8. Prompt、Agent、Tool、检索链路的可观测性；
9. JWT、RBAC、多租户、文档权限、脱敏和审计；
10. 异步入库、任务队列、进度查询、失败重试和断点恢复；
11. Docker 部署、健康检查、限流、缓存、监控和告警。

## 四、每个模块的实施流程

```text

→ 运行验证
```

每个模块必须记录：

- 正常案例；
- 失败案例；
- 验收结果；
- 技术债务；
- 面试问法与回答。

## 五、代码协作边界

学习和实验阶段统一使用：

```text
code/backend/tests/cs.py
```

原有 `app.py`、`rag_graph_chat.py` 和正式接口暂不干扰。实验完成并理解后，再迁移到正式模块并重构。

### 代码修改红线

- 所有代码必须由用户亲自写入文件；
- Codex 只能在聊天窗口提供代码示例、插入位置、修改范围和验证方法；
- 未经用户明确提出“请直接修改代码”或同等明确授权，Codex 不得使用工具创建、修改、删除或重构任何代码文件；
- 即使用户要求“继续”或“开始”，也只能继续提供下一段示例，不能直接落盘；
- 文档、计划和验收记录可以由 Codex 按用户要求维护，但不得借此修改业务代码；
- 用户明确授权直接修改时，只执行授权范围内的最小改动，并在完成后报告具体文件和验证结果。

## 六、工作原则

1. 目标优先，不主动扩展需求。
2. 能执行就直接执行，不反复确认。
3. 不解释基础知识，除非用户询问。
4. 修改代码前先理解现状，不随意重构。
5. 遇到问题只报告关键原因和解决方案。
6. 输出简短，优先给结论和下一步动作。
7. 不重复已经确定的信息。
8. 先分析当前状态，再给最小必要操作。
9. 修改后总结修改内容、验证结果和下一步。
10. 不把“代码写出来”当成“功能完成”。
11. 不隐藏异常、警告和未验证部分。
12. 不擅自提交、推送、合并或删除内容。

## 七、晚间小目标规则

每次只设定一个可运行、可观察、可验收的小目标。今晚当前目标是：

```text
为 cs.py 的 Agent / ToolNode 图增加结构化日志，
并验证“普通问候不调用 Tool”和“法律问题调用 Tool”两条分支。
```

验收必须能看到：

- 每一步的 State；
- Agent 的 tool_calls；
- 路由结果；
- Tool 输入和输出；
- 最终回答。

## 八、面试准备标准

每完成一个模块，都要能回答：

1. 为什么需要这个模块？
2. 不使用它会有什么问题？
3. 它在数据流中的位置是什么？
4. 输入输出是什么？
5. 出错如何处理？
6. 如何测试？
7. 如何扩展到生产环境？
8. 当前实现和企业级实现差在哪里？
9. 为什么选择当前技术？
10. 如果流量、数据量或模型成本增加，如何改造？

## 九、最终端到端验收

```text
上传文档
→ 异步处理
→ 清洗切分
→ 混合检索
→ Reranker
→ Agent 选择 Tool
→ Tool 执行
→ 引用生成
→ 答案校验
→ 前端展示
→ 全链路追踪
```

最终准备：

- 正常演示链路；
- 无资料拒答链路；
- Tool 失败链路；
- 模型失败链路；
- 权限拦截链路；
- 架构图；
- 面试问答清单。
